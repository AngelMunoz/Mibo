## What this does

Restructures the docs around the two program runtimes and documents the adaptive architecture end to end.

### Structure

- **`docs/mvu/`** — the MVU guides move here: Elmish, programs, commands, subscriptions, system pipeline, headless, service composition, scaling, MonoGame migration. Cross-links fixed; v1 references updated.
- **`docs/adaptive/`** — a new section mirroring the MVU coverage, written as guidance with full runnable examples: overview, programs, intents, subscriptions, systems, scaling, services, headless, background work, derived state.
- **`docs/mibo-adaptive/`** — the `Mibo.Adaptive` incremental-computation library documented as its own package: overview, values, collections, threading, performance.
- **Patterns** — runtime-specific patterns (composable systems, background work, pre-computed state) move under MVU; pooled particles and layered rendering stay (both runtimes register renderers identically). Each MVU pattern page links its adaptive counterpart.
- **Scaling** — splits per runtime: the MVU complexity ladder under `mvu/`, a new adaptive ladder under `adaptive/`.

### Sidebar / navigation

- Categories ordered by subject: Architecture, MVU, Adaptive, Mibo.Adaptive, then Documentation, Migrating, and the feature sections (Level Design, Rendering, 2D/3D, Amenities, Patterns).
- Fixed the pre-existing `categoryindex` collisions (Migrating vs Level Design both 2; 3D Rendering vs Amenities both 5) and the `animation3d`/`commands` index tie.
- The v1 archive leaves the sidebar (categories stripped) and is linked from the front page; `assets.md` no longer carries the stale `categoryindex: 5` that was rendering a stray top-level Amenities.

### Tooling

- `fsdocs-tool` bumped 21.0.0 → 22.1.0.
- `docs.yml` builds with `--ignoreuncategorized` so uncategorized pages don't render an "Other" category.

### Notes

- Adaptive pages are written standalone (no migration framing), named functions with partial application, `GameConfig.withTitle`-style config, cohesive full examples.
- The `force` vs `getValue` decision is documented as architecture guidance in Programs plus the reference table in the library Collections page.
- `Derived State` teaches the projection organization pattern (in-feature vs top-level `Projections`, build-once-at-init), not library basics.
